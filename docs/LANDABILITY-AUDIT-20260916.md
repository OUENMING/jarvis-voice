## 1. 落地性：依赖轮子矩阵（✅ 本机实测 PyPI 元数据）

| 包 | 最新版 | requires_python | macOS arm64 轮子 | 结论 |
|---|---|---|---|---|
| **pywebrtc-audio**（AEC3 绑定） | 0.2.0 | >=3.10 | **cp310 / cp311 / cp312 / cp313 / cp314 全有** | ✅ **现有 3.14.7 venv 直接可装** |
| livekit（含 rtc.APM） | 1.1.18 | >=3.9 | py3-none-macosx_11_0_arm64 | ✅ 可装（AEC 备选路径） |
| sherpa-onnx（VAD/ASR） | 1.13.8 | >=3.7 | cp38–cp314 全有 | ✅ 已装 1.13.7，可用 |
| onnxruntime | 1.30.0 | >=3.11 | cp311–cp314 | ✅ |
| **kokoro-onnx** | 0.6.1 | **<3.14** | **无 arm64 轮子**（纯 py + sdist） | ⚠️ **与 3.14 venv 不兼容 → 本地 Kokoro 需 ≤3.13 旁路 venv** |
| kokoro | 0.9.4 | **<3.13** | 无 | ⚠️ 更严 |
| **pipecat-ai-smart-turn / smart-turn** | — | — | **PyPI 上不存在** | ⚠️ **Smart Turn 必须从 GitHub 源码 vendor**（`model.py` + `inference.py` + HF 权重），没有 pip 安装路径 |
| silero-vad | 6.2.1 | >=3.8 | 纯 py | ✅ |
| pyaec（speexdsp） | 1.0.1 | >=3.6 | 视 PyPI | 🟡 可装但质量低于 AEC3、且近两年未更新 → 不作首选 |

### 由此产生的三条落地订正

1. **Python 版本分裂问题比预想小。** 主 venv（3.14.7）能装 AEC、VAD、ASR、云 TTS 客户端、onnxruntime。**只有"本地 Kokoro 兜底"需要 3.12/3.13 旁路 venv**——若默认 TTS 走云，这条可以推迟到"做离线兜底时再做"。→ **P0 的 0.7 项（建 3.12 venv）从"必须"降级为"仅兜底需要"。**
2. **Smart Turn 没有 pip 包** → 落地方式是 vendor 源码 + 从 HuggingFace 拉权重。工作量约 1 小时，但要记进 P1 任务（含 3.12 依赖，因为它官方要求 3.12 —— **因此 Smart Turn 也大概率放进那个旁路 venv，主 venv 只跑 Silero VAD**）。
3. **AEC 有现成路**（见下），不需要动 Swift/PyObjC。

## 2. AEC 落地路径（🔗 专项调研）

**结论：可行，但"装上就好"是错觉——上限由硬件锁死。**

| 方案 | 可装性 | 效果 | 判定 |
|---|---|---|---|
| **`pywebrtc-audio`** 0.2.0（2026-09-03 发布，AWS strands-labs 维护） | ✅ pip，含 cp314 arm64 轮子 | AEC3，`process(near, far)` + `stream_delay_ms`，内置延迟估计 | ✅ **首选** |
| `livekit.rtc.AudioProcessingModule` | ✅ 含在 livekit 内，**不需要 LiveKit 服务端** | 同一套 AEC3，强制 10ms 帧 | ✅ 并列首选 |
| Apple VoiceProcessingIO | 需 PyObjC/Swift 助手 | AEC 质量最好 | ❌ **不推荐**：输出静默变 9 声道（无文档、导致 `EXC_BAD_ACCESS`）、自动 duck 其它音频、不可动态启停、AEC 收敛需 500ms–2s、有 3–6s 静音丢失实例 |
| 神经 AEC（RNNoise/DeepFilterNet/Krisp） | — | **是降噪不是 AEC**（无 far-end 参考，消不掉自己的声音） | ❌ 不能替代 |
| 纯软件门控（播放时降 VAD 灵敏度 + cooldown） | 零成本 | 没有真 barge-in | 🟡 仅兜底 |

**已被验证的实现范式（ARGUS，与本项目栈完全一致）**：`sounddevice` 全双工 Stream、16kHz / **160 样本（10ms）**、`process_reverse_stream(outdata)` → `process_stream(indata)` 同一回调内完成、`set_stream_delay_ms(100)`。
实测：合成 440Hz 音调降 **94.7%**；**内置扬声器播放真实 TTS 预期 ~70–85%**。作者明确警告：**不要自己加外部延迟缓冲**，会与 WebRTC 内部对齐打架。

**🔴 必须知道的硬件天花板**：`py-xiaozhi` 官方文档原话——*"笔记本内置麦克风+扬声器组合由于物理振动耦合，AEC 效果有限，推荐外置 USB 麦克风 + 独立扬声器"*。
→ **工程上按"~70–85% 降噪"设计，不按 100% 设计。** 现实选项：外置麦/独立音箱（推荐）、耳机（最省事但牺牲免提感）、AEC + 半双工门控 + 唤醒词打断（Pipecat 模式，兜底）。

**附带参照**：LiveKit Agents 的 `aec_warmup_duration` **默认 3.0 秒**——即 AEC 就绪前不接受打断。说明"开头几秒打不断"是行业普遍现象，不是我们的 bug。

## 3. 网络实测（✅ 本机裸 TCP，注意方法论）

⚠️ **先说一个方法陷阱**：`curl` 的 `time_connect` 显示 0.3ms（本地代理介入），不可用。改用裸 socket 后：

| 目标 | 真实 RTT（中位） | 解读 |
|---|---|---|
| api.anthropic.com | **6.5 ms** | 都柏林本地 anycast 边缘。**这就是 CC 延迟不高的原因** |
| generativelanguage.googleapis.com | 8.1 ms | 同上（本地边缘） |
| api.openai.com | 8.5 ms | 同上 |
| api.minimax.io | 8.4 ms | 边缘近（Azure Front Door anycast）⚠️ **但源站在哪未知** |
| **dashscope-intl.aliyuncs.com（阿里新加坡）** | **179.3 ms** | 无 Dublin 边缘，真·跨洲 |

**关键教训：TCP 到边缘的 RTT ≠ API 端到端延迟。** 首三行只能说明"连得上、边缘近"，**接上真实 API Key 后的首包延迟仍必须实测**。唯一现在就能确定的是：**阿里新加坡方向的物理往返 ≥176ms**（单程 ~88ms），流式 TTS 每个音频块都要跨这一趟。

→ **落地订正**：我之前把阿里国际站定为"默认云 TTS"是基于**单价**（¥0.95/万 vs MiniMax ¥4.3/万）。但**跨洲 176ms 会直接加到首音延迟上**。这两家必须**用真 Key 各测一遍首包延迟**再定默认档——单价贵 4 倍 vs 首音慢 176ms，是要用耳朵和秒表决定的，不是用价目表。
（另：MiniMax 的 `api.minimax.io` 边缘在 8ms 内，若其源站也在欧美，它可能**同时**拿下低延迟和高单价里的一半优势——⚠️ 待测。）

## 4. 实现效果：四个需求逐项研判

| 需求 | 能否达标 | 依据与条件 |
|---|---|---|
| **播报忠实**（逐字念 CC 结果） | ✅ **结构性达标** | TTS 读文本，无中间模型改写。这是整条路线最硬的胜利 |
| **不自言自语** | ✅ **结构性达标** | 级联无空转 decode、无 KV 污染。构造上不可能（对比：双脑时代花了整整一周才定位） |
| **能打断** | 🟡 **能，但受硬件限制** | AEC 主路 0.5–2 天可落（§2）；**上限 ~70–85% 降噪**。笔记本内置扬声器高音量下可能"打不断/误打断"仍偶发 → 现实预案：外置麦/音箱，或降级为"唤醒词打断"（Pipecat 模式）。**这不是软件没做好，是物理耦合** |
| **像正常聊天（<1.5s）** | ❌ **达不到原目标** | 实测 CC 首句 1333–3069ms（见 `VERIFY-AND-BRAINSTORM` §2）。端到端首音现实值 **1.8–4.2s**。补救：填充音（感知 <500ms）+ 切句调优 + 快路小模型；**内容延迟仍会落在 2–3s**。要不要接受，是产品决策不是技术决策 |

**另一项要提前认知的效果**：`ttft` 744–1316ms 与"首句"1333–3069ms 之间的差距，来自 `claude_bridge.py` 的切句门槛（标点 + ≥4 字符）。**切句策略是零成本的最大延迟杠杆**，P0 就该试。

## 5. 前沿性评估（诚实版）

### 什么是前沿的（2026 SOTA）

| 组件 | 前沿性 | 证据 |
|---|---|---|
| **Smart Turn v3.2** | ✅ **真 SOTA** | audio-native 语义端点（直接吃 PCM、利用韵律）、23 语言含中文、int8 8MB、CPU 最快 10ms/云端 ~65ms、**数据集+训练脚本+权重全开源**、2026-01 更新。设计上"配合 Silero、只在静音期跑"——正是我们 P1 的设计 |
| **投机打断（EagerEOT + abort）** | ✅ 2026 前沿范式 | Deepgram Flux 参考实现；企业级 backchannel 走独立小通道 |
| **双 LLM 快路** | ✅ 前沿实践 | Claudia Voice（本地 MoE 快路 + Claude 深路） |
| **克隆音色做身份统一** | ✅ 当前最佳实践 | embedding 缓存后推理期零额外成本 |
| **情感旁路闭环** | 🟡 **空白区** | 组件成熟（SenseVoice 标签 + instruct TTS），但"标签→persona 调制→情感 TTS"完整闭环**没有知名开源参考**；EMA 平滑亦无论文 → 这是可以自己定义前沿的地方 |

### 什么不是前沿的（以及为什么无所谓）

- **级联骨架本身不前沿**。绝对前沿是端到端全双工（Moshi/PersonaPlex/MiniCPM-o 4.5）。但：
  1. VoiceAgentBench 实证：**agentic 任务上级联 > SpeechLM**（arXiv 2510.07978，已核实原文）；
  2. 生产环境仍以级联/hybrid 为主；
  3. **端到端全双工对本项目有一个致命缺陷：不能忠实朗读脚本**（拍了一个月才拍实的结论）。
  → **刻意不追前沿，是有代价意识的选择，不是落后。**
- 但必须承认代价：**级联天然慢一拍**（打断要经过 VAD→取消→重听），且丢失原生副语言。这是买到"可信+可控"付的钱。

### 一句话定位

> **成熟骨架 + 前沿外围；在"能不能朗读、能不能打断、会不会自言自语"这三条上，我们站在可靠性一侧而不是前沿一侧——这是清醒的取舍。**

## 6. 风险矩阵：什么会杀死这个项目

| 风险 | 概率 | 后果 | 缓解 |
|---|---|---|---|
| **笔记本内置麦+扬声器 AEC 不够** | 中高 | 打断体验差 → 核心需求受损 | 外置麦/音箱（首选）、耳机、或降级唤醒词打断；**提前按 70–85% 设计** |
| 延迟感知不达标 | 中 | "不像聊天" | 填充音 + 切句调优 + 快路小模型；**接受 2–3s 内容延迟** |
| 云 TTS 跨洲 176ms（阿里） | 高 | 首音变慢 | **用真 Key 实测再定默认档**；MiniMax 边缘近、待测源站 |
| 云单点故障/限流 | 中 | 临时变哑 | 多提供商路由 + 本地 Kokoro 兜底（需 3.13 venv） |
| CC 用量/限流（~100–200 turn/天） | 中 | 被限速 | 双模型路由 + 应答词过滤 + 预算护栏 |
| Python 3.14 vs 生态（kokoro/Smart Turn 要 3.12/3.13） | 高但已知 | 装不上 | **旁路 venv（≈30 分钟）**，且只在兜底/Kokoro/Smart Turn 时用 |

## 7. 要不要开工？——我的建议

**能落地、效果预期要说清楚，然后就能开工。** 具体：

1. **P0 立刻可做**（无需任何云 Key）：主 venv 里装 `pywebrtc-audio` + 落 Silero VAD + SenseVoice + `claude_bridge` + 切句调优 → 先跑通"派活→逐字播报"。
2. **并行半天实验**：AEC ERLE 实测（播 TTS 同时录音，**在你实际会用到的音量下**）——这是唯一能证伪的测试，也决定打断体验的上限。
3. **拿到云 Key 后各测一次**：阿里国际 / MiniMax 国际的首包延迟（都柏林侧），用秒表定默认 TTS 档。
4. **认可度检查**：上面「像正常聊天」这一条我判定**达不到原目标**。如果你要求 <1.5s，那需要重新讨论（选项：接受 2–3s+填充音 / 上 Tier 2 云端 V2V 语音壳 / 放弃"零感知延迟"预期）。
