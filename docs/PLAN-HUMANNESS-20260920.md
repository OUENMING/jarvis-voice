# 对话「人味」方案（2026-09-20）

> **触发**：Owen「这个机器人虽然说像口语一样的终端，但是在对话上还是少了点人味」
> **方法**：先读既有结论（`RESEARCH-NATURALNESS-20260916.md`）→ 行业调研 → **拿项目自己的数据定量** → 出方案
> **口径**：🟢 本机一手实测 / 可复现　🟡 单源二手（标日期）　🔴 未验证

## 0. 三句话

1. **诊断**：助手每轮说 **110 字**（中位；均值 167，最大 527），用户说 **10 字** —— **11 倍**。真人在 1–2 倍。
   ⚠️ **2026-09-21 更正**：本条原先写的是「75 字 / 7.5 倍」，**与真机实测不符** ——
   用 `~/.jarvis/events.jsonl` 按回合统计（43 个回合）：**中位 110 字 / 6 句**、
   打断时 `played_s` 中位 **22.4s**（最大 47.2s）。换算 ≈26 秒/轮，
   是 CHI 2022「话多基线 4.03 秒」的 **~6 倍**。详见 `PLAN-SHORT-TURNS-20260920.md`。
   17% 的句子 >120 字，**占了全部字数的 72%**。它不是"不会说人话"，是**一次说太多**。
2. **两条已核实的机制性缺陷**（都在本轮查明）：
   - **切句器被换行卡死** → 每轮的后半段根本切不开（41/41 长句都是最后一句）✅ 本轮已修
   - **`is_backchannel` 永远来不及生效** → 打断由 VAD 起音驱动、转写晚到，
     于是**一句「嗯」就能让助手停下**（41 次早打断里大量是「嗯/うん/那个。」这类）
3. **外部证据直接印证**：Waseda Talking Turns（2026-09-13）测出现有语音系统
   「**rarely backchannel**」；行业 2026 困难清单里「full-duplex naturalness
   （graceful overlap, **backchanneling**, reliable mid-thought interruption）」
   与我们的短板完全重合。**这不是你项目的个案。**

## 3. 方案（按投入产出比排序）

### ✅ P0 —— 修切句器（**本轮已完成**）

**机制**：消费掉一句后 `buf` 往往以 `\n` 开头，而 `\n` 在 `SENT_END` 里 →
`find('\n') == 0` → `0 < NEXT_SENT_MIN(4)` → **立刻 break，之后再也不会切** →
本轮剩余内容全卡在 `buf`，最后在 `result` 处**整块不切**吐出去。

**证据**：`41/41` 条 >120 字的 `sentence` 事件**全部是每轮最后一句**，位置统计 `{'最后一句': 41}`，零例外。

**影响**：首句仍能提前出声（`first_ms` 看起来正常），但**第二句往后要等整段生成完才开始合成** —— 切句本来就是为了避免这件事。

**已做**：`claude_bridge._split_sentences` 循环内 `lstrip(SENT_END + 空白)`；
`tests/test_split_sentences.py`（9 组用例，旧代码 7 条失败 —— red-green 已验证）。

**收益**：不改变说了多少字，但**后半段更早出声**、句级指标恢复可信。
⚠️ **真机未验证** —— 验收：跑一场，看 `sentence` 事件里还有没有 >120 字的。

---

### ✅ P1 —— 打断误判恢复（**本轮已完成**）

**问题**（🟢 本轮核实）：`filler.py` 的 docstring 写着用途是
「**不要因为一句"嗯""对"就打断正在播报的助手**」，
但它在 `_brain_once` 里、**转写到达时打断早就发生了**（打断由 VAD 起音驱动，不等转写）。
**这个模块声明的目的从来没实现过。**

**数据**：41 次早打断（<3 秒）里大量是 `'嗯。'` `'うん。'` `'.'` `'那个。'` 这类 —— 用户只是在应答。

**做法**（照抄 LiveKit `false_interruption_timeout` 的语义）：

```
VAD 起音 → ① 立即 暂停播放（**保留缓冲**，不销毁）    ← 感知上的即时响应不变
            ↓ 等转写（bargein_grace_ms = 800ms 窗口）
        ② 转写是 backchannel / 回声 / 空  → **恢复播放**（不重做 CC 那一轮）
        ③ 转写是真心话            → **提交打断**（丢弃缓冲 + 作废轮次 + brain.interrupt）
        ④ 窗口内没等到任何转写     → 提交（否则会永远卡在暂停）
```

**已落地的改动**：

| 文件 | 改动 |
|---|---|
| `player.py` | 🆕 `pause()` / `resume()` / `is_paused` —— **保留 `_buf`**（`flush()` 是销毁）。回调暂停时输出静音、且**不记 underrun**（那是我们主动叫停的）|
| `config.py` | 🆕 `bargein_grace_ms: int = 800`（取值依据写在注释里）|
| `filler.py` | 🆕 `is_false_interruption()` —— **刻意不合并进 `is_backchannel`**（两者契约不同）；`_BACKCHANNEL` 补 `うん/うう/嗯ん` 这些 ASR 错听变体 |
| `orchestrator.py` | `_do_interrupt` 拆成 `_begin_bargein`（只暂停）/ `_commit_interrupt`（不可逆）；主循环的**自动**打断走宽限、**明说的路径仍是立即提交**；`_brain_once` 在最前面解决待决窗口 |

**⚠️ 一个连线时容易漏的顺序**：待决窗口必须在 `_brain_once` 的**最前面**解决 ——
回声护栏 / 停口令 / 元命令那些分支都会 `return`，放在它们之后就**永远不解决**，
主循环超时一提交，助手还是停了。而最该撤回的那一类（`'那个。'`/`'让我想想。'`）
恰恰**会被回声护栏拦下** —— 所以回声护栏的结论要**先算出来、传给**这个判断
（只判一次，否则 `suppressed` 计数还会翻倍）。

**验收**：`tests/test_bargein_recovery.py`（30 条断言，旧行为下 7 条失败 —— red-green 已验证）；
`test_bargein_latency` **未退化**（暂停是即时的，感知延迟仍是 400ms）。

**🔴 真机未验收**：窗口值 800ms 是按链路时延推的，**没在真机上调过**。
验收方法：播报中只「嗯」一声 → 助手**不应该停**；说真话 → 仍应在 400ms 内停。
**代价**：误判撤回时，一句话中间会多一个约 0.8s 的顿 —— 要 A/B 才知值不值。

### ✅ P2 —— 轮次协商：说一段，停一下，等反应（**机制已交付，值未验**）

**这是「人味」的核心缺口**（自然度调研早就点出「缺重叠说话/轮次协商」），
而且**本架构能做**、代价小：

```
第 N 句播完（默认第 2 句）→ 等播放器排空 → 主动停 `turn_yield_ms`
   · 用户在这段停顿里开口 → 走正常打断（现成机制，不用改）
   · 用户没开口 → 自动继续下一句
```

**为什么这是"人味"而不只是"加停顿"**：它把「一次说完」变成「**留出插话的槽位**」。
用户不必"抢"话，而是被**邀请**接话。这也是 CUI'25 那条「延迟 >4s 是头号杀手」的反面应用 ——
**可控的短停顿 ≠ 静默**，静默是"它在想"，停顿是"它在等你"。

**⚠️ 默认 0（关），而且是刻意的**：停顿是**净增加**的时间（3 句 × 600ms = +1.8s）。
**用户不接话就是纯亏。** 所以这次只交付**机制**，值不值要 A/B 量过再定，甚至可能整体否掉。
这是它排在 P1 之后的原因，也是它**与「延迟 >4s」那条结论的直接张力**。

**实现**（`orchestrator._maybe_yield_turn()`）：数当前轮已播几句；到阈值时
`while player.is_playing(): sleep` → `sleep(yield_ms)`。**不需要任何新机制** ——
打断由主循环独立处理，用户在停顿里开口 → `_begin_bargein` → 提交 →
`session.interrupt()` → 下一句的 `is_current` 判假 → TTS 自然停。
另外三件防护都做了：**等这一句真播完再停**（别从中间切断）／
**后面没句子了就不让**（让给谁？）／**等待期间被打断就别让**。

**A/B 用法**（同场景各跑一场）：
```bash
JARVIS_TURN_YIELD_MS=600 ./jarvis.sh start --speaker-aec --dashboard   # 开
./jarvis.sh start --speaker-aec --dashboard                            # 关（默认）
```
看三件事：① **总时长**变长多少 ② **用户真的接话了吗**（仪表盘 `turn_yield` 事件之后
有没有紧跟 `user`）③ 听感上是「在等我」还是「卡了」。

**验收**：`tests/test_turn_yield.py`（6 组用例覆盖机制边界）—— 验的是**机制正确**，
"该不该开"只能真机听。

### 🥉 P3 —— 助手发 backchannel（用户说话时「嗯」）

**社区最高 ROI 的一项，但对我们的优先级偏低** —— 理由是我们自己的数据：
**用户话长中位只有 8 字、p90 24 字**（≈2–5 秒语音），
**很少说得长到需要一个中途 backchannel**。

**如果做**，参数可直接抄（⚠️ 只是工程调参，**没有研究背书**）：
`min_speech_before_eligible_s=0.7` / `cooldown_s=2.5` / `fire_probability=0.8` / 停顿 >0.2s。
⚠️ 它自己注明：停顿分析需要**与端点检测相反**的时序设置，推理开销约 **2×**，
且「**measure before a large deployment**」。

🔴 **中文取值全网查不到**（嗯/对/是的频率与时序），照搬英文有风险 → 要做就得先自己测。

**架构可行性**（已核）：播放走现成的 `player.write_filler()` ——
far 参考（`_cb` 里镜像）✅、回声护栏（`note_spoken(text, filler=True)`）✅ 都自动覆盖。
**但有一个状态机约束**：`_play_filler` 要求 `state is THINKING`，
而用户说话时 state 是 `IDLE` —— **播 backchannel 绝不能把 state 改成 SPEAKING**
（否则主循环的 barge-in 判据 `st is not State.IDLE` 失效，打断会失灵）。

### ❌ 不做（有证据否定）

| 项 | 为什么 |
|---|---|
| **主动追问 / 主动闲聊** | ProVoice-Bench（arXiv 2604.15037）实测 **over-triggering 是主要失败模式**；CUI *Proactivity Dilemma*（15 人访谈）多人场合「**干扰、剥夺能动性**」 |
| **重叠说话（真全双工）** | 需要**流式 ASR**，我们是非流式 SenseVoice。DuplexCascade 是研究级 SOTA（arXiv 2603.09180） |
| **换 LiveKit 的 Turn Detector** | 许可禁止 standalone（见 §2） |
| **长回答"落屏"** | 🔴 **我原本想推荐，但想清楚后否掉**：仪表盘**本来就渲染全文**（`sentence` 事件的 `text`），基础设施已有；可真人在**语音场景下不看屏幕** —— 落屏是"伪解决"。真问题是**说太多**，该治的是长度本身（prompt）与轮次协商（P2） |

## 5. 与既有结论的关系

- 自然度调研（09-16）结论「**对话拟人度只能到约七成**，缺重叠说话/副语言/轮次协商」
  **仍然成立**，本方案是**在这个 70% 内部做改进**（P1 治误判、P2 补轮次协商槽位），
  **不是**去冲那 100%（那要换架构）
- 「延迟 >4s 是头号杀手」（CUI'25）与 **P2 的停顿有直接张力** ——
  所以 P2 的停顿必须短、必须单点、必须 A/B。**这是我把它排在 P1 之后的原因**
