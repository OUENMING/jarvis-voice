## 1. 打断延迟：600ms → 400ms

**现象**：用户两次反馈「打断不灵敏」，第二次说「好很多了，就是还得大点声」。

**先排除的**（🟢 离线实测，未开任何音频设备）：

| 假设 | 实测 | 结论 |
|---|---|---|
| VAD 起点检测需要很大声 | 增益 0.15（≈ -16dB）仍 +300ms 触发 | ❌ 与音量无关 |
| AEC 在双讲时压低近端 | 保留率 0.83–0.87（≈ -1.2~-1.6 dB） | ❌ 太小，不是主因 |
| SNR 门限在播放期抬高 | `need` 恒为 `vad_min_rms`=0.012 | ❌ 没抬高 |

**真因**（`tests/test_bargein_latency.py` 锁住）：

```
语音起点 → VAD 翻 True        +300ms   ← sherpa 要等 min_speech=0.25s 连续语音
        → interrupt_confirm  +300ms   ← 第二次确认，**冗余**
        = 打断触发            +600ms
```

`interrupt_confirm_ms` 防的瞬态噪声，Silero 自己就拦得住：**60/100/150/250/400/600ms
的宽带噪声爆发（30× 噪声底）一次都没翻 True**。改成 100ms → **+400ms**。

**剩下 250ms 的代价**：`vad_min_speech` 同时决定"多短的段算话"，要再快得动它，另算。

**"得大点声"的真因**（另一个）：插话的转写**系统性变差** ——

| | 中位字数 | ≤2 字碎片 |
|---|---|---|
| 插话（打断后）n=98 | **6** | **26%** |
| 平常（无打断）n=90 | 13 | 10% |

碎片是 `'那个。'` `'嗯。'` `'嗯ん。'` —— **助手自己的填充音被麦克风收回去**（填充音原文
就是 `["嗯……", "那个……", …]`），且**全聚在填充音开始后 +1.4~1.7s**。≤2 字碎片里
**47%** 紧跟填充音（正常转写只有 22%）。→ 用户拿到一堆幻听碎片，只好说大声点。

**修法**：填充音从没进过回声护栏（只写播放、不登记文本），而 `min_len=6` 也拦不住
2 个字的「那个」。现在填充音走**独立短窗口通道**（只跟最近 3s 播过的填充音精确比对）。

## 2. 元命令双向都错（真机 188 条转写里挖出来的）

### 2.1 三次**漏判**：「清空」被听成别的，但「上下文」完好

主人试过 5 次这个命令，**3 次完全没反应**：

| 真机转写 | 结果 |
|---|---|
| `'轻松一下上下文。'` | ❌ 漏判（清空→**轻松**）|
| `'星空上下文。'` | ❌ 漏判（清空→**星空**）|
| `'供上下文。'` | ❌ 漏判（清空→**供**）|
| `'清空上下文。'` | ✅ |
| `'嗯，清空一下上下文。'` | ✅ |

旧判据要求「**动作词 + 宾语**」，而动作词恰好是被听坏的那一半。
→ 改成「**上下文**单独出现即成立」（这个词日常对话几乎不用，它自己就是判据）。

**离线复核**（TTS 合成 6 个语速/音色，生产配置 900ms 预滚）：**6/6 首字或尾字判错**
（星空上下文 / 清空上下凉 / 星空上下人 / 清空上下轮 / 清空上下门）——
说明这不是偶发，是短命令的**系统性弱点**（短句没有上下文，SenseVoice 只能猜）。

**顺带发现预滚是脆的**：同一句「清空上下文」在 0/300/**600/900**/1200ms 预滚下分别得到
「星空上下文 / 星空上下文 / **清空上下文 / 清空上下轮** / 星空上下文」 —— **1200ms 反而更差**
（环里可用的"话首之前"样本不够，切片被静默跳过）。900ms 落在有效带里，保持不动。

### 2.2 一次**误判**：他在**问**，系统却清了

`'你还还你还记得清空上下文之前说的什么吗？'` —— 主人是在问助手记不记得，
旧判据只看到「清空」+「上下文」就执行了。**上下文真被清了。**

→ 加两道护栏（都取「宁可漏判不可误判」的方向）：
**疑问句不是命令** + **长句不是命令**（实测触发的几条归一化后是 4–9 字，取上限 10）。

⚠️ 代价：`'你能帮我清空兑换吗？'`（ASR 把「上下文」听成「兑换」）现在**也不会触发** ——
但它在旧判据下本来也不触发，不是回归。

## 3. `memory.md`：一个只读的死文件

**现象**（用户在 2026-09-20 提出「我希望我重要的事情它都能记住」）：
`~/.jarvis/memory.md` 的**读**链路一直是通的（`_compose_system_prompt()` 把它注进系统提示），
但全库**没有任何写入路径** —— 上线至今 **0 条内容**，只有模板注释。
Aries 自己在日志里说：

> 「我自己那份可写记忆，是空的。里面只有一句模板注释，一条实际内容都没有。」

**为什么这件事重要**：`--resume` 默认开（跨重启记得），但 `/clear` 会把会话历史整个丢掉，
且实测**这条链是永不重置的**（见 §4）。所以 `memory.md` 是**唯一**能跨「清空/重启」留下的地方。

**修法**（🟡 社区做法：LangChain 2026-04-09 的 `/remember`、LangGraph handbook 的
「explicit requests + **search-before-write**」）：**显式请求 → 确定性追加**，不押模型自觉
（本项目提示词规则 14 的遵守率实测只有 **22%**）。

- `commands.py` 新增 `remember` 元命令（触发词须在**句首附近**；疑问句排除）
- `orchestrator._remember()`：写成 `- YYYY-MM-DD 内容`；**去重**复用 `echoguard.similarity`
- **绝不自动删**（硬规矩：不删用户数据）—— 超 120 条只提醒，压缩交给人

**两个设计细节**（都会踩）：

1. **写成功也要继续送 CC。** 元命令本来是"就地吃掉"的，但那样 CC 在**本会话内**就不知道
   这件事（五分钟后再问「我下周三要干嘛」它答不上来）。所以 `_run_meta` 现在返回
   「是否已处理完」：`remember` 写成功返回 `False`（继续送 CC），其它返回 `True`。
2. **写失败**不能既本地出声又 fall through —— `_speak_local` 会 `begin_turn()`，
   紧接着 CC 那轮再 `begin_turn()` 会把提示作废（同一类坑见 `session.py` 的注释）。

**⚠️ 未验证的缺口（社区明确警告过）**：🟡 LangChain 2026-06-24 ——
「若运行时缓存了 prompt，memory 的写入必须有**刷新路径**，否则系统存对了却一直拿旧上下文跑」。
我们正是这样：`_compose_system_prompt()` **只在启动跑一次**，所以写进去的内容
**下次启动才进系统提示**。会话内不等它（CC 看得见这轮对话），跨会话靠重启。

## 4. 上下文膨胀：实测数据（支撑上面的判断）

用户的疑问：「这个项目只有一条对话，跑久了上下文必然太多吧？」**成立**，且已量化。

| 项 | 值 |
|---|---|
| `--resume` 链上最长的一个会话 | `c81985d0` |
| 跨度 | 09-16 20:15 → 09-19 21:24 = **73.2 小时同一个会话** |
| 用户轮次 | **215** |
| 累计内容 | **≈370,618 token**（工具输入/输出 **1,436,496 字符** = 大头）|
| **压缩边界 / 摘要** | **0 / 0** |

**250+ 个 jarvis 脑会话全扫过，压缩边界和摘要统统是 0 —— 自动压缩一次都没触发过。**

370K 已越过已知的缓存悬崖（>250K 时前缀缓存命中崩到 0–7%，见全局记忆
`llm-prompt-cache-cliff`），而「对话感」是这个项目的第一目标。

**为什么不用 Jev 解这个**（用户提过两次）：
- **生态确实成熟**：LiteLLM 2026-09-18 发了官方博客把 Jev 压缩做成内置 guardrail
  （`relevance_threshold: 0.2`，问「这个旧工具结果回答最新问题还用得上吗」）；
  `tamaratran/fast-jev-compaction` ★4,280
- **但它解的是"删"，不是"记"**：官方描述原文「everything kept stays **verbatim**」——
  只删工具结果，**用户和助手的话永不删**，也**不写任何新东西**（Jev 设计上不生成文本）
- **且我们的触发源是 0**：那个插件挂 `session.compact`，而我们的压缩从未触发 → 它一次都不会跑
- 用户描述的「Jev 告知 LLM 怎么做 → LLM 记住 → 再压缩」是**官方支持的混合模式**
  （Pydantic AI 集成），形状没问题 —— 但那是 **A 侧（压）**，与 **B 侧（记）** 无关

### 4.1 ✅ 根因已查实：自动压缩**根本没有武装**

**判定函数的第一道闸是「窗口来源 ≠ `auto`」**，来源解析顺序：
`env > settings > 服务端下发（仅 firstParty）> … > 内置 model 表 > auto`。
**我们走 cc-switch 代理 → 拿不到服务端窗口表 → 来源落到 `auto` → 直接 return，
阈值根本不算。**

本机双向验证（2.1.278，bridge 的真实命令行 + `--debug`）：

| 配置 | debug 日志里的 `autocompact` |
|---|---|
| 生产配置（无窗口变量） | **0 条**（只有一条无关的 auto-mode 日志）|
| 加 `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000` | **`autocompact: level=ok effectiveWindow=180000`** |

**第二个后果更严重**：窗口不设 → 撞上限时只能靠 **reactive 兜底**（API 返回 too-long 时触发），
而**代理会改写错误文案 → 那条兜底不生效 → 脑硬挂**。

**修法**：`config.brain_compact_window`（默认 200000，env `JARVIS_BRAIN_COMPACT_WINDOW`）
→ `ClaudeBridge` 把它作为 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 传给子进程。
取 200000 = Claude Code 对 `claude-haiku-4-5` 的标称窗口；**真实后端实测 63.9 万 token
的请求仍返回 200**，所以 200K 是保守选择（代价只是压缩早一点，有损；不保守的代价是硬挂）。

### 4.2 为什么必须治：上下文越大，首字越慢（本机 11,245 条真实请求）

数据源：`~/.cc-switch/cc-switch.db` 的 `proxy_request_logs`（当前 provider = commandcode
→ `deepseek/deepseek-v4.1-flash`）。

| input tokens | n | 首字 p50 | 缓存命中率 p50 |
|---|---|---|---|
| 0–20K | 10750 | **1295 ms** | **99.5%** |
| 20–50K | 210 | 984 ms | 32.6% |
| 50–100K | 89 | 1211 ms | 19.3% |
| 100–200K | 70 | 1640 ms | 9.5% |
| 200–300K | 82 | **1969 ms** | **5.7%** |
| 300–600K | 43 | **2431 ms** | 5.3% |
| ≥600K | 1 | 2894 ms | 2.2% |

→ **首字从 1.3s 涨到 2.0–2.4s（约 1.8×），缓存命中率从 99.5% 崩到 5.7%。**
这个项目的第一目标是「对话感」，所以「上下文只增不减」是直接打在主目标上的。

⚠️ **对既有记忆的修正**：全局记忆 `llm-prompt-cache-cliff` 记的是「>250K 时缓存崩到 0–7%」，
但本机本次实测显示**崩塌从 20K 就开始了**（20–50K 已掉到 32.6%）。
两个数字口径不同（可能是不同模型/别名），引用时以**本机当次实测**为准。

### 4.3 仍未做：重置策略

`--resume` 默认开 + 单一 session_id = 一条永不重置的对话。现在有了 A 侧兜底（自动压缩），
但**压缩是到达窗口才触发**，日常仍会跑在 100–180K 区间（≈1.6–2.0s 首字）。

更激进的做法是**确定性重置**（超 N 轮 / N 小时就 `/clear`），把上下文压在 20K 以内
（≈1.3s 首字、99% 缓存命中）。现在 `memory.md` 可写了，跨清空的记忆有了落点，
这条路才真正可行。**但「用多少连续性换多少延迟」是产品决策，留给 Owen。**
