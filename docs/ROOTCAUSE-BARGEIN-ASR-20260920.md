# 打断时识别差：根因定案（2026-09-20）

> **触发**：用户报「静音打断识别没问题，但它一说话我再打断，识别率就很低」。
> **结论**：🟢 **WebRTC AEC3 在双讲时削掉近端语音的高频（辅音），物理原因已排除。**
> 全部证据可离线复现，无需音频设备。

---

## 0. 一句话

**麦克风收到的原始信号是好的（4–8k 高频 13–17.5%，与真人录音同级）；
过完 AEC 就只剩 0.1–0.3%。** 辅音全在高频 → 「上」听成「创」、「清」丢掉、
「中秋节」被猜成韩文。**不是管道问题、不是模型问题、不是麦克风问题 —— 是 AEC。**

---

## 1. 真机证据（同一句的 AEC 前后对照）

`AecGate` 在打断落盘音频时**同时存两份**：`bargein.wav`（过 AEC）与 `bargein-raw.wav`（未过）。

| 录音 | 过 AEC 质心 | **未过 AEC 质心** | 过 AEC 4–8k | **未过 4–8k** |
|---|---|---|---|---|
| #1 | 591 Hz | 833 Hz | 0.3% | 2.4% |
| #2 | 547 Hz | **1639 Hz** | 0.1% | **13.0%** |
| #3 | 641 Hz | **1852 Hz** | 0.3% | **17.5%** |
| 对照·模型自带真人录音 | 1556 Hz | — | 11.6% | — |

**未过 AEC 的高频与真人录音同级甚至更好 → 笔记本麦与距离都没问题。**

配套排除的证据：

| 假设 | 结论 | 证据 |
|---|---|---|
| 音频被污染/截断 | ❌ | 剖面：前 700ms 预滚静音 + RMS 2403 的清晰语音，峰值 0.64、**无削顶** |
| 管道把音频弄坏了 | ❌ | 同一段音频**离线重转 3/3 复现同样的错** |
| SenseVoice 模型不行 | ❌ | 同样的短语用 TTS 念 → **5/5 全对**（含「上周做了什么」「清空上下文」）|
| AEC 消回声不工作 | ❌ | 真机 **ERLE 中位 34.5 dB**（离线探针报 34–36 dB）|

## 2. 离线控制实验（拿模型的真人录音过 AEC，完全可复现）

| 配置 | 谱质心 | 4–8k |
|---|---|---|
| 不过 AEC | 1609 Hz | 12.0% |
| **AEC + far 有信号** | **895 Hz** | **2.1%** ← 高频掉 **5.7×** |
| **AEC + far 静音** | 1652 Hz | 12.3% ← **完全无害** |

- **是 AEC3 本身**：关 NS、关 HPF 都没变化；单独跑 `EchoCanceller`（不带任何包装层）结果一样
- **没有旋钮可调**：`pywebrtc_audio` 只暴露 `sample_rate / num_channels / stream_delay_ms`
- **事后 EQ 救不回来**：+6/12/18/20 dB 都试过，输出仍是 `'创周做了什么？'` —— 损伤是非线性的

### 2.1 它的压制强度取决于「能不能用 far 解释近端」

| far 场景 | 谱质心 | 4–8k |
|---|---|---|
| 不过 AEC（基线） | 1514 Hz | 10.6% |
| far 延迟 **0ms**（far 与 near 完全相关） | 1656 Hz | 6.9% ← 损伤最小 |
| far 延迟 50ms | 828 Hz | 1.7% |
| far 延迟 150ms（**= 我们生产用的值**） | 872 Hz | 2.9% |
| far 延迟 300ms | 1131 Hz | 5.6% |
| **far = 无关噪声** | **442 Hz** | **0.1%** ← 最惨 |

**它解释不了近端时，就越狠地压。** 而我们的 `aec_stream_delay_ms=150` 是**估计值** ——
错一点就掉进 1.7–2.9% 那一档。**这是一个可以调优的旋钮（先试这个，最便宜）。**

## 3. 顺带查明的两件事

### 3.1 VAD 起音比真实开口晚 ~500ms

轨迹曲线：用户 **-507ms** 就开口了（麦克风能量 571→989→1273），而 `vad.speaking`
到 **0ms** 才翻 True。离线测（TTS 音频）只有 +300ms —— 真人起音是渐强的，Silero 要更久。
**打断"迟钝"的主因是这个，跟识别差是两回事。**

### 3.2 P1 的「误判撤回」机制几乎不生效

真机 25 次打断里 **22 次是 `[打断-超时] 800ms 内没有转写`** —— 转写要等
VAD 端点（`min_silence_duration=0.5s`）+ ASR，实测 **1.5–2s** 才到。
功能上不影响（超时后照样提交），但**那条防误判的设计是空转的**。

**更该改的是判据而不是窗口**：
- 用户说 **<800ms 就停** → 像 backchannel，**再等等**
- 连续说 **≥800ms** → 肯定是真打断，**立即提交**

## 4. 修复方向（**需要决策**）

| 方案 | 代价 | 说明 |
|---|---|---|
| **A. 调 `aec_stream_delay_ms`** | 小 | 现在 150 是估计值。扫一遍找 ERLE 最好 / 高频损失最小的值。**可能只缓解不根治**（150ms 档本身就有 2.9% 损失）|
| **B. 自研线性 AEC** | 中 | far 参考**完美**（我们确切知道在播什么）→ 只做线性抵消、不做非线性压制 → 理论上不伤近端。⚠️ 我的快速 NLMS 原型**发散了**（残余 1030%），要正经做+测 |
| **C. 换现成 AEC** | 中 | SpeexDSP 等更保守的实现；要重做对齐、重测 ERLE |
| **D. 接受** | 0 | 现状：打断能停，但打断时说的话识别差 |

**⚠️ 无论选哪个，"打断"这个交互的固有代价是**：用户的话与它的话重叠 →
要么留回声（ASR 更差）、要么被 AEC 压（辅音丢失）。**完全无损的双讲需要另一类算法。**

## 5. 诊断基建（本轮新增，都可复用）

| 件 | 作用 |
|---|---|
| `bargein_trace.py` | 常驻记麦克风/far 电平 + VAD 状态（10Hz，只进内存）；关键时刻落盘前 15 秒 → `~/.jarvis/bargein-trace.jsonl` |
| 同上的 `save_pcm` | 打断音频落盘（过 AEC / **未过 AEC** 两份）→ `~/.jarvis/bargein-audio/` |
| `player.far_rms()` | 扬声器侧电平 → 能算**真实房间的 ERLE** |
| `aec.raw_slice(n, end_offset)` | 取未过 AEC 的原始近端（`end_offset` 必需：VAD 等静音才吐段，段里的音频比"此刻"早 0.5s）|

关掉：`JARVIS_BARGEIN_TRACE=0`。

⚠️ **写第一版时踩的坑**：`raw_slice(len(utt))` 不带偏移 → 拿到的是**段之后**的窗，
互相关只有 0.10–0.34、滑移不一致 → **A/B 完全无效，还得出过相反的结论**。
