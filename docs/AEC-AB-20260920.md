# AEC 双讲保真：离线 A/B 结果 + 真机验收步骤（2026-09-20）

> **触发**：`ROOTCAUSE-BARGEIN-ASR-20260920.md` 定案「打断时识别差 = WebRTC AEC3
> 双讲时削掉近端高频」，四条修复方向待选。本文是**把选择做成实验**的结果。
> **一句话**：离线 20 个合成双讲场景，`speex` 线性后端转写错误率 **8.0%**，
> `webrtc` **39.8%** —— 差 **5 倍**。⚠️ 但这是**合成**场景，真机验收还没做。

---

## 1. 决策：从「四选一」收敛到「真机 A/B 一次」

原文的四条方向里，**A（调 `aec_stream_delay_ms`）** 已被 §2.1 的数据弱化：
150ms 那一档本身就有 2.9% 的高频损失，且损伤来自 NLP，**换延迟只能缓解、不能根治**。

**B（自研线性 AEC）** 的原型发散过（残余 1030%）。查源码后发现**不必自研** ——
见下。

**C（换现成 AEC）** 落地成了一个更具体的东西：

| | `webrtc`（现行默认） | `speex`（新增，可切） |
|---|---|---|
| 实现 | `pywebrtc-audio` / WebRTC AEC3 | `pyaec` → `aec-rs` → **SpeexDSP** |
| 结构 | 自适应滤波 **＋ NLP 残余抑制** | **只有线性**抵消，**无残余抑制** |
| 单讲消回声 | **强**（合成纯回声 57 dB） | 弱（同条件 11 dB） |
| 双讲保近端 | ⚠️ **差** | ✅ 好 |

### 为什么 `pyaec` 的 `enable_preprocess=False` 正是"纯线性"

读 `speexdsp/libspeexdsp/mdf.c` 一手确认（§关键源码）：

- `speex_echo_cancellation()` 的输出是 `麦克风 − 滤波后回声`；
  **它自己不施加频谱后滤波** —— `power_1[]` 是**自适应步长**，不是输出增益。
- 会压近端的**残余回声抑制在 `speex_preprocess_run()` 里**，由 `speex_echo_get_residual()` 驱动。
- aec-rs 把这层做成开关：`Aec(..., enable_preprocess=False)` 就是**只做线性抵消**。
- `nm -gU` 核实：`libaec.dylib` **只导出 3 个 `Aec*` 符号**，`speex_echo_ctl` 进不去 →

⚠️ **`pyaec` 在 16 kHz 下有个改不掉的缺陷**：aec-rs 从不调
`SPEEX_ECHO_SET_SAMPLING_RATE`，Speex 内部**永远认为采样率是 8000**
→ `beta0 = 2·frame_size/8000` 比 16k 的正确值**大一倍**（泄漏翻倍）→ 收敛上限被压低。
**这不是用法错误**，是包装层的信息丢失。它正是"牺牲单讲换双讲"的来源。

**D（接受）** 保留为兜底，但现在有更好的选项。

## 2. 离线结果（🟢 可复现，一条命令）

`tools/aec_ab.py`。合成：近端 = 一段**干净真人录音**，远端 = **另一段无关语言**的真人录音
（`en/ja/ko/yue/zh` 两两配对），回声 = far 延迟 150ms × 增益 0.5。
判据是 **SenseVoice 的字符错误率**（Levenshtein），不是任何信号指标。

```
变体                       总错字  总字数   错误率
pyaec-lin(fl=3200)           53     660     8.0%     ← 最好
pyaec-pre(fl=3200)           62     660     9.4%
pyaec-lin(fl=6400)           71     660    10.8%
webrtc(d=0ms)               263     660    39.8%     ← 现行默认
```

**20/20 个场景**里 `webrtc` 都更差或持平 —— 不是偶发。

加 **60ms far 参考失配**（模拟「150ms 是估计值」）后结论不变（40 场景 1320 字）：
`pyaec-lin` **7.3%** vs `webrtc` **40.5%**。

### 2.1 ⚠️ 一个被顺带否掉的指标：**近端 SDR 预测不了转写**

同一次合成里三种变体的 **near-end SDR 几乎相同**：

| 变体 | near-end SDR | 转写错误率 |
|---|---|---|
| webrtc | −0.6 dB | **39.8%** |
| pyaec-lin | −0.7 dB | **8.0%** |
| pyaec-pre | −0.1 dB | 9.4% |

`cozec/aec` 基准用近端 SDR 给算法排序（FDAF 8.0 dB vs WebRTC −1.8 dB）。
**在本项目上，这个指标对转写的区分度是零** —— 三种损伤不同（一个被门掉、一个留残余回声），
SDR 却撞在一起。原文档已警告「SDR 高 ≠ 转写准」；这里是更强的版本：**它测不出来**。
⇒ **以后选 AEC 只准用真 ASR，别用任何信号级代理指标。**

### 2.2 实时性不是问题

`pyaec` 收 Python list，每帧要 `(c_int16*n)(*list)`，本来担心跑不动。
实测（`frame=160, fl=3200`）：**0.08 ms/帧**，需 100 帧/s → **CPU 占用 0.8%**。

### 2.3 已保存的真机音频：⚠️ 复现不了原文档的绝对值

现存 3 对（`~/.jarvis/bargein-audio/`，14:42–14:56）能确认的：

| | 4–8k 占比（raw） | 4–8k 占比（过 AEC） | 转写 |
|---|---|---|---|
| #1 | 0.01% | 0.00% | raw「看到了看到了。」/ AEC「看到了看看到了。」 |
| #2 | 0.22% | 0.00% | raw「啊，先停一下。」/ AEC「好，可以提一下。」 |
| #3 | 0.06% | 0.00% | raw「的是那篇好的好处。」/ AEC「好的好的。」 |

**方向一致**（过 AEC 的高频总是更低），但：
1. **绝对量级对不上原文档**（原文 raw 4–8k 是 2.4–17.5%，这里只有 0.01–0.22%）。
   原因大概率是**当时的分析脚本没进仓库**，度量口径（频带/分母/是否分帧）已丢失。
   ⇒ **原文那几张表的绝对值，事后无法复算** —— 引用时要标注这一点。
2. **转写差异很小且方向混合**（#3 反而是 AEC 更干净）。
   这三段都是**极短**打断（「好的好的」量级），信息量不足以分辨。

⇒ **存活的真机证据不足以支撑结论。** 这正是下面这一步必须做的原因。

## 3. 真机验收（**一步，需要你**）

代码已就位，**默认行为不变**（`aec_backend` 默认 `webrtc`）。

```bash
cd ~/jarvis-voice

# 第一轮：现行默认（拿基准 + 落 far 三件套）
./jarvis.sh start --speaker-aec

# 第二轮：换线性后端（同样的操作：说几句让它回，然后中途打断）
JARVIS_AEC_BACKEND=speex ./jarvis.sh start --speaker-aec
```

**横幅会显示当前后端**（`AEC[webrtc]` / `AEC[speex]`）—— 一眼确认切没切。
（`JARVIS_AEC_BACKEND` 拼错会**响亮报错**，不静默退回。）

每轮打断几次即可。**两种后端都会落盘三件套**，所以第一轮的数据也能离线复算第二轮：

```
~/.jarvis/bargein-audio/<stem>-bargein.wav      过 AEC（当时真正送去 ASR 的那份）
                        <stem>-bargein-raw.wav  未过 AEC 的原始麦克风（含 500ms 预滚）
                        <stem>-far.wav          当时实际喂给 AEC 的 far 参考   🆕
```

三份共用同一个 `<stem>`（`HHMMSS-mmm`）→ **配对靠文件名，不用猜**。

然后离线复算（**不用再跑真机**）：

```bash
.venv/bin/python tools/aec_ab.py --pair <stem>-bargein-raw.wav <stem>-far.wav \
                                --post-aec <stem>-bargein.wav
```

它会并排列出：原始麦克风 / WebRTC / Speex / 生产实际输出 四条的**转写**。

## 4. 怎么判读（**只看转写**）

- ✅ `speex` 明显更准时 → 把 `aec_backend` 默认值改成 `speex`，删掉另一个后端
- ❌ 没差别 → 说明真机上「AEC 压近端」不是主因，**回去查 VAD 起音（晚 ~500ms）**
  和 P1 判据（22/25 超时）—— 那两条是独立的问题，可能才是"打断迟钝"的真凶
- ⚠️ 若 `speex` 出现「它自己说的话被转写进来」→ 是**线性 AEC 单讲消不干净**的代价，
  此时用 **`far` 是三件套之一**这一点做文本层兜底（`echoguard`），或调 `JARVIS_AEC_SPEEX_FL`

⚠️ **`ERLE` 在这一步毫无用处** —— 双讲下不适用（ICASSP AEC Challenge）。
只需要新生成的 `<stem>-bargein.wav.txt`（转写）与离线复算表。

## 5. ⚠️ 第一次真机验收：**一份音频都没落盘**（当天抓到并修掉）

跑完 `--speaker-aec` 那一轮，`~/.jarvis/bargein-audio/` **一个新文件都没有** ——
日志里没有 traceback、也**没有**任何"失败"提示。纯沉默失败。

**根因**：保存判据原来是

```python
if self.session.state is not State.IDLE or self._pending_bargein_at is not None:
```

而 `_commit_interrupt()` → `session.interrupt()` 会把 state **置成 IDLE**，超时分支又会
**清掉** `_pending_bargein_at`。时间线：

| 时刻 | 发生什么 | 两个判据 |
|---|---|---|
| T+0 | VAD 起音 → `_begin_bargein()` 开 800ms 窗口 | 真 |
| T+800ms | `[打断-超时]` → 清窗口 + state→IDLE | **全假** |
| T+1.5~2s | 转写才到（VAD 要等 `min_silence_duration` 才吐段）| 全假 → **不存** |

⇒ 这个诊断**只在转写快过 800ms 时才工作**。老那轮存下来是因为「看到了看到了」382ms
就到了；这轮句子长（「呃，等一下，你知道那个明天天气怎么样吗？」）**八次全超时**，
而**超时正是最常见的那条路**（真机 22/25）。

**修法**：诊断用自己的时间戳 `_bargein_utt_at`，**跨状态重置存活**；在 `_brain_once` 里
**读一次就清**，且放在**所有提前 return 之前**（段太短被丢时也要清，否则会标到下一句）。
窗口 `BARGEIN_UTT_WINDOW_S = 30s` —— 用户可以在打断后继续说很久。

**配套**：存不下来时**要在日志里出声**（`[打断] ⚠️ 音频没存下来`），
别让诊断再沉默失败一次。

**回归测试**：`tests/test_bargein_audio_capture.py`。做过 red-green ——
换回旧判据后这三条**真的红了**（`got=[]`），精确复现真机的失败。

## 6. 已知边界（别当成结论）

- 🔴 **合成 ≠ 真机**：无真实房间混响、无笔记本麦频响、far 是另一段干净语音而不是 Fish TTS
- 🔴 **真机 A/B 尚未做**（本文 §3 就是它）
- 🟡 合成用**纯延迟+增益**回声（`--rir` 可传实测 RIR，尚未采）
- 🟡 每段只有 ~5 秒 —— AEC 收敛期占比偏大（`--repeat` 可加长）
- 🟡 `pyaec` 的 8kHz 采样率缺陷是**包装层**的，若上游修了结论可能变化
