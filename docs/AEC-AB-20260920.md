## 1. 决策：从「四选一」收敛到「真机 A/B 一次」

原文的四条方向里，**A（调 `aec_stream_delay_ms`）** 已被 §2.1 的数据弱化：
150ms 那一档本身就有 2.9% 的高频损失，且损伤来自 NLP，**换延迟只能缓解、不能根治**。

**B（自研线性 AEC）** 的原型发散过（残余 1030%）。查源码后发现**不必自研** ——
见下。

**C（换现成 AEC）** 落地成了一个更具体的东西：

| | `webrtc`（现行默认） | `speex`（新增，可切） |
|---|---|---|
| 实现 | `pywebrtc-audio` / WebRTC AEC3 | `pyaec` → `aec-rs` → **SpeexDSP** |
| 结构 | 自适应滤波 **＋ NLP 残余抑制** | **只有线性**抵消，**无残余抑制** |
| 单讲消回声 | **强**（合成纯回声 57 dB） | 弱（同条件 11 dB） |
| 双讲保近端 | ⚠️ **差** | ✅ 好 |

### 为什么 `pyaec` 的 `enable_preprocess=False` 正是"纯线性"

读 `speexdsp/libspeexdsp/mdf.c` 一手确认（§关键源码）：

- `speex_echo_cancellation()` 的输出是 `麦克风 − 滤波后回声`；
  **它自己不施加频谱后滤波** —— `power_1[]` 是**自适应步长**，不是输出增益。
- 会压近端的**残余回声抑制在 `speex_preprocess_run()` 里**，由 `speex_echo_get_residual()` 驱动。
- aec-rs 把这层做成开关：`Aec(..., enable_preprocess=False)` 就是**只做线性抵消**。
- `nm -gU` 核实：`libaec.dylib` **只导出 3 个 `Aec*` 符号**，`speex_echo_ctl` 进不去 →

⚠️ **`pyaec` 在 16 kHz 下有个改不掉的缺陷**：aec-rs 从不调
`SPEEX_ECHO_SET_SAMPLING_RATE`，Speex 内部**永远认为采样率是 8000**
→ `beta0 = 2·frame_size/8000` 比 16k 的正确值**大一倍**（泄漏翻倍）→ 收敛上限被压低。
**这不是用法错误**，是包装层的信息丢失。它正是"牺牲单讲换双讲"的来源。

**D（接受）** 保留为兜底，但现在有更好的选项。

## 2. 离线结果（🟢 可复现，一条命令）

`tools/aec_ab.py`。合成：近端 = 一段**干净真人录音**，远端 = **另一段无关语言**的真人录音
（`en/ja/ko/yue/zh` 两两配对），回声 = far 延迟 150ms × 增益 0.5。
判据是 **SenseVoice 的字符错误率**（Levenshtein），不是任何信号指标。

```
变体                       总错字  总字数   错误率
pyaec-lin(fl=3200)           53     660     8.0%     ← 最好
pyaec-pre(fl=3200)           62     660     9.4%
pyaec-lin(fl=6400)           71     660    10.8%
webrtc(d=0ms)               263     660    39.8%     ← 现行默认
```

**20/20 个场景**里 `webrtc` 都更差或持平 —— 不是偶发。

加 **60ms far 参考失配**（模拟「150ms 是估计值」）后结论不变（40 场景 1320 字）：
`pyaec-lin` **7.3%** vs `webrtc` **40.5%**。

### 2.1 ⚠️ 一个被顺带否掉的指标：**近端 SDR 预测不了转写**

同一次合成里三种变体的 **near-end SDR 几乎相同**：

| 变体 | near-end SDR | 转写错误率 |
|---|---|---|
| webrtc | −0.6 dB | **39.8%** |
| pyaec-lin | −0.7 dB | **8.0%** |
| pyaec-pre | −0.1 dB | 9.4% |

`cozec/aec` 基准用近端 SDR 给算法排序（FDAF 8.0 dB vs WebRTC −1.8 dB）。
**在本项目上，这个指标对转写的区分度是零** —— 三种损伤不同（一个被门掉、一个留残余回声），
SDR 却撞在一起。原文档已警告「SDR 高 ≠ 转写准」；这里是更强的版本：**它测不出来**。
⇒ **以后选 AEC 只准用真 ASR，别用任何信号级代理指标。**

### 2.2 实时性不是问题

`pyaec` 收 Python list，每帧要 `(c_int16*n)(*list)`，本来担心跑不动。
实测（`frame=160, fl=3200`）：**0.08 ms/帧**，需 100 帧/s → **CPU 占用 0.8%**。

### 2.3 已保存的真机音频：⚠️ 复现不了原文档的绝对值

现存 3 对（`~/.jarvis/bargein-audio/`，14:42–14:56）能确认的：

| | 4–8k 占比（raw） | 4–8k 占比（过 AEC） | 转写 |
|---|---|---|---|
| #1 | 0.01% | 0.00% | raw「看到了看到了。」/ AEC「看到了看看到了。」 |
| #2 | 0.22% | 0.00% | raw「啊，先停一下。」/ AEC「好，可以提一下。」 |
| #3 | 0.06% | 0.00% | raw「的是那篇好的好处。」/ AEC「好的好的。」 |

**方向一致**（过 AEC 的高频总是更低），但：
1. **绝对量级对不上原文档**（原文 raw 4–8k 是 2.4–17.5%，这里只有 0.01–0.22%）。
   原因大概率是**当时的分析脚本没进仓库**，度量口径（频带/分母/是否分帧）已丢失。
   ⇒ **原文那几张表的绝对值，事后无法复算** —— 引用时要标注这一点。
2. **转写差异很小且方向混合**（#3 反而是 AEC 更干净）。
   这三段都是**极短**打断（「好的好的」量级），信息量不足以分辨。

⇒ **存活的真机证据不足以支撑结论。** 这正是下面这一步必须做的原因。

## 3. 真机验收（**一步，需要你**）

代码已就位，**默认行为不变**（`aec_backend` 默认 `webrtc`）。

```bash
cd ~/jarvis-voice

# 第一轮：现行默认（拿基准 + 落 far 三件套）
./jarvis.sh start --speaker-aec

# 第二轮：换线性后端（同样的操作：说几句让它回，然后中途打断）
JARVIS_AEC_BACKEND=speex ./jarvis.sh start --speaker-aec
```

**横幅会显示当前后端**（`AEC[webrtc]` / `AEC[speex]`）—— 一眼确认切没切。
（`JARVIS_AEC_BACKEND` 拼错会**响亮报错**，不静默退回。）

每轮打断几次即可。**两种后端都会落盘三件套**，所以第一轮的数据也能离线复算第二轮：

```
~/.jarvis/bargein-audio/<stem>-bargein.wav      过 AEC（当时真正送去 ASR 的那份）
                        <stem>-bargein-raw.wav  未过 AEC 的原始麦克风（含 500ms 预滚）
                        <stem>-far.wav          当时实际喂给 AEC 的 far 参考   🆕
```

三份共用同一个 `<stem>`（`HHMMSS-mmm`）→ **配对靠文件名，不用猜**。

然后离线复算（**不用再跑真机**）：

```bash
.venv/bin/python tools/aec_ab.py --pair <stem>-bargein-raw.wav <stem>-far.wav \
                                --post-aec <stem>-bargein.wav
```

它会并排列出：原始麦克风 / WebRTC / Speex / 生产实际输出 四条的**转写**。

## 5. ⚠️ 第一次真机验收：**一份音频都没落盘**（当天抓到并修掉）

跑完 `--speaker-aec` 那一轮，`~/.jarvis/bargein-audio/` **一个新文件都没有** ——
日志里没有 traceback、也**没有**任何"失败"提示。纯沉默失败。

**根因**：保存判据原来是

```python
if self.session.state is not State.IDLE or self._pending_bargein_at is not None:
```

而 `_commit_interrupt()` → `session.interrupt()` 会把 state **置成 IDLE**，超时分支又会
**清掉** `_pending_bargein_at`。时间线：

| 时刻 | 发生什么 | 两个判据 |
|---|---|---|
| T+0 | VAD 起音 → `_begin_bargein()` 开 800ms 窗口 | 真 |
| T+800ms | `[打断-超时]` → 清窗口 + state→IDLE | **全假** |
| T+1.5~2s | 转写才到（VAD 要等 `min_silence_duration` 才吐段）| 全假 → **不存** |

⇒ 这个诊断**只在转写快过 800ms 时才工作**。老那轮存下来是因为「看到了看到了」382ms
就到了；这轮句子长（「呃，等一下，你知道那个明天天气怎么样吗？」）**八次全超时**，
而**超时正是最常见的那条路**（真机 22/25）。

**修法**：诊断用自己的时间戳 `_bargein_utt_at`，**跨状态重置存活**；在 `_brain_once` 里
**读一次就清**，且放在**所有提前 return 之前**（段太短被丢时也要清，否则会标到下一句）。
窗口 `BARGEIN_UTT_WINDOW_S = 30s` —— 用户可以在打断后继续说很久。

**配套**：存不下来时**要在日志里出声**（`[打断] ⚠️ 音频没存下来`），
别让诊断再沉默失败一次。

**回归测试**：`tests/test_bargein_audio_capture.py`。做过 red-green ——
换回旧判据后这三条**真的红了**（`got=[]`），精确复现真机的失败。

## 7. 🔴🔴 真正的「自己打断自己」根因：**喂给 AEC 的 far 参考一直是坏的**

**用户报**：「自己打断自己的现象很严重」。

**真机证据**（`~/.jarvis/bargein-audio/` 三件套，16:1x）：

| stem | 送去 ASR 的（过 AEC） | raw 麦克风 | **far（助手当时在说的）** |
|---|---|---|---|
| 161739-623 | `Yeah.` | `掐了另一次。` | **`把自己拆了，另一次是。`** |
| 161620-927 | `What.` | `上下还在雷雨。` | **`30度上下还在雷雨。`** |
| 161703-436 | `う确6。` | `20度最热的白。` | **`高度20度，最弱的白。`** |
| 161922-731 | `5爱0。` | `一路爱尔兰。` | **`口进一目，爱尔兰斯。`** |

麦克风里**全是它自己的声音**，AEC 一点没消掉，ASR 转出一段乱码，系统当成用户插话
→ 打断自己 → 再播 → 再被自己打断。49 次打断里 **25 次发生在 `state=thinking`**
（当时只有填充音在播）。

**量出来的 far 参考**：`RMS 32750 / 32767`，**54% 的样本贴在 ±32767** ——
那不是音频，是**方波**。

### 7.1 根因：`accept()` 里漏了一次归一化

```python
far44 = player.far_slice(...)                    # int16，±32767
far16 = resample_poly(far44.astype(np.float32))  # ← 漏了 / 32768，仍是 ±32767
far_i16 = np.clip(far16 * INT16, ...)            # ← 再乘 32768 → 全部截到满幅
```

数值复现：输入 RMS 2121 → **输出 RMS 32572、49.4% 贴满幅**；
加回 `/ INT16` → 输出 RMS 2121、0% 贴满幅。

⚠️ **不是今天引进的**：`git show HEAD:jarvis_voice/aec.py` 里就有 ——
**生产的 AEC 从上线起就没拿到过可用参考**。之前的 34–36 dB ERLE 全是
`tests/aec_probe.py` 自己造参考测的，**没走过这条路径**。

### 7.2 它如何推翻本文档 §1–§2 的因果归属

`ROOTCAUSE` §2.1 那张表里最惨的一档就是
**「far = 无关噪声 → 质心 442 Hz / 4-8k 0.1%」**。
**一份饱和方波对 AEC 来说就是无关噪声** —— 生产一直跑在这一档。
本文观察到的「过 AEC 后 4–8k 只剩 0.1–0.3%」与那一档**几乎完全吻合**。

⇒ **「AEC3 双讲时固有地压近端」这个结论必须重新评估。**
AEC3 拿到**正常**参考时是否仍这样压近端，**未验证**。

### 7.3 老测试为什么没抓到

`tests/test_aec_gate.py` 的集成断言只到 `player.far_slice()`（原始镜像，
尺度本来就对），**从没检查 `accept()` 内部真正交给 AEC 的那份**。
（它还有一个更隐蔽的问题：用 1024 帧驱动 `_cb`、而 `accept()` 每次消耗 4410 帧
→ 读指针与镜像不同步 → 连内容对不对都查不了。）

**新测试** `tests/test_aec_far_scale.py`：用**间谍后端**接住 `process()` 收到的 far，
断言 ① 与源同尺度（±3 dB）② 不饱和 ③ 与源相关 > 0.9。
`block_frames=4410` 让播放与消费同步。**已过 red-green**（去掉 `/ INT16` → 4 条红）。

## 9. 真机三个实验的结果（2026-09-20 傍晚）

用 `tools/measure_echo_delay.py` —— 通过**生产同一个 Player/MicStream** 放一段
**啁啾**、同时录。用户不出声 ⇒ 麦克风里**只有回声** ⇒ 「消得干不干净」是一个
**无歧义的数（残差能量）**，不需要任何相关性判据。

### ② 延迟：**150ms 是对的，不用调**

| far 读偏移 | 消掉 |
|---|---|
| 100ms | 43.1 dB |
| **150ms（现行）** | **43.3 dB** |
| 200ms | 43.3 dB |
| 250ms | 33.9 dB |
| 300ms | 15.6 dB |
| ≥350ms | ≤10 dB |

**150ms 落在一片 100–250ms 的最优平台上**，且是平台中心附近。**`aec_stream_delay_ms` 不用改。**

⚠️ **顺带查明一个结构性约束**：`d < 100ms` 的读法是**非法的** —— far 窗口会越过
「已播出」边界被截断（`far_slice` 读不了未来）。评测里 25ms 那个"最好"的值就是
这个假象。（更极端的 `d=0` 恒返回空数组 —— 代码注释里早写过这条。）

### ③ 后端：**Speex 不能用 —— 撤回本文 §1–§2 的推荐**

同一次真机录音（7.2s 纯回声）上比两个后端：

| 后端 | 消掉 |
|---|---|
| **WebRTC AEC3**（生产默认）| **43.3 dB** ✅ |
| Speex 线性 fl=3200 | **−0.5 dB**（等于没消）|
| Speex 线性 fl=6400 | −0.8 dB |
| Speex 含残余抑制 | 0.3 dB |

🔴 **结论翻转**：§2 那个「Speex 8.0% vs WebRTC 39.8%」是**合成场景**（纯延迟+增益回声），
在**真实房间混响**下 Speex **一分贝都消不掉**（它的 8kHz 采样率固有缺陷扛不住）。
⇒ **不要切 `JARVIS_AEC_BACKEND=speex`。** 那个开关保留，但**默认值与推荐值都是 `webrtc`**。

⚠️ **这份文档 §1–§2 的建议（换线性 AEC）就到这里作废。** 留着的价值是方法论：
**合成基准可以在真实房间上完全翻转**，所以任何后端选型都必须过一遍真机回声。

### ① 音量假设：**实测否掉**（不是回声造成的）

用户假设「音量开得越大 → 误打断越多」。用**多电平啁啾**（同一段信号按 6 档幅度放，
等价于调音量但可复现）实测 —— 播放电平跨 **20 dB（10 倍幅度）**：

| 播放幅度 | far | 过 AEC 后残余 | 消掉 | 越过 VAD 门限 0.012？ |
|---|---|---|---|---|
| 0.15 | −30.7 | −73.7 | 42.9 dB | 否 |
| 0.30 | −26.8 | −72.8 | 45.9 dB | 否 |
| 0.50 | −22.7 | −66.0 | 43.3 dB | 否 |
| 0.80 | −18.2 | −70.3 | 52.1 dB | 否 |
| 1.30 | −14.1 | −70.9 | 56.8 dB | 否 |
| 2.00 | −10.3 | −64.6 | 54.3 dB | 否 |

**残余回声始终比门限低 20–100 倍**（−64 dBFS vs 门限 −38.4 dBFS）。
再查**起音瞬间**（AEC 还没适应新信号的假设）：8 段起音，后 0–100ms 的残余
−66 ~ −74 dBFS，**同样全部远低于门限**。

⇒ **单讲下回声不可能触发 VAD。** 「音量越大越容易误打断」**不成立**。

⚠️ **我之前的"字符串铁证"只证明了麦克风听得见扬声器**（那是 `raw`，未过 AEC）——
**没证明过完 AEC 还留着**。实测反过来：有一条捕获 `raw` 是清晰的回声
（`那几个我跳过去`）而过 AEC 后**全空**（ASR 只出 `.`）→ **AEC 把回声消干净了**。

⇒ **误打断的成因还没找到。** 剩下的唯一候选是**双讲**（用户与它同时说话时
AEC3 的抑制会下降 / NLP 会压近端）—— **这个仍未测**，
正确做法是**放啁啾的同时让人说话**（啁啾不是语音，互相关的零假设对照是干净的）。

### 附：`far 读偏移 < 100ms` 结构性非法（**别调**）

`far_slice` 读不了未来：偏移 < 100ms（`far` 窗宽 100ms）时窗口会越过
「已播出」边界被截断 → 拿到的是**错位的半截**。实测 `d=25ms` 看起来"最好"
就是这个假象。**`aec_stream_delay_ms` 必须 ≥ 100ms**（现行 150ms 是对的）。

## 10. 🟢🟢 双讲标定 —— **结论坐实了**（3 轮配对，2026-09-20 傍晚）

**协议**（`tools/measure_echo_delay.py --double-talk --repeat 3`）：
同一段文本每轮念**两遍**（一遍安静、一遍扬声器同时放**带限噪声**），
再比两遍的 ASR **字符错误率**。`--repeat N` 做**配对**对照（每轮都有安静组+双讲组）。

**为什么用噪声不用啁啾**：重复啁啾的互相关是**梳状峰**（间隔=重复周期）→ 会选错齿 →
far 整体错位整数个周期 → 结果全假。噪声自相关近似 delta：对齐唯一，且满带激励。
（写完第一版才发现 —— 这是必须记下的坑。）

### 结果（两次，条件不同 —— **看后一行**）

**A. 噪声电平没标定（回声比语音高 6-8 dB）**

| 轮 | 安静 CER | 双讲 CER | 倍数 |
|---|---|---|---|
| 1 | 9.7% | 33.3% | 3.4× |
| 2 | 5.6% | **70.8%** | **12.8×** |
| 3 | 8.3% | **87.5%** | **10.5×** |
| 均值 | **7.9%** | **63.9%** | **8.1×** |

**B. 噪声**闭环标定**到与语音同级（回声到麦 − 语音 = +1.6~+2.5 dB）—— 🟢 这才是生产代表的数**

| 轮 | 安静 CER | 双讲 CER | 倍数 |
|---|---|---|---|
| 1 | 6.9% | 18.1% | **2.60×** |
| 2 | 8.3% | 23.6% | **2.83×** |
| 3 | 6.9% | 29.2% | **4.20×** |
| **均值** | **7.4%** | **23.6%** | **3.19×** |

**⇒ 真实幅度 ≈ 3.2 倍**（A 的 8.1× 是回声偏大造成的，不能引用）。
三轮全部有效、全部更差。残余回声 −71.7 ~ −73.7 dBFS，**全部低于 VAD 门限**。

**错处是同一个签名**：「先看了会书」→「**去开会书**」；
「窗**外**有几只鸟在叫」→「**突然有几十鸟在叫**」；「上周**寄**的」→「**上把上手等**这」。

### 10.0 ⚠️ 「噪声电平」必须**闭环实测**，不能用常数

第一版我拿「声学衰减 ≈14 dB」当常数去算噪声电平 → 实测出来回声比语音**高 6-8 dB**，
完全不是"同级"。同一个房间同一天，实测衰减从 **7.6 到 14 dB** 都出现过。
⇒ 改成**闭环**：先放一小段**已知电平**的噪声、用户保持安静 → 直接量出衰减 → 再定电平。
（两声叮 = 别说话。）

**而且噪声电平必须**整轮锁定**。** 我第一版每轮都按那一轮的语音重算 →
用户朗读一波动噪声就跟着变，**轮与轮之间不可比**（真人当场听出来「两遍噪音不一样」）。

### 10.0.1 ⚠️ 有效性检查：安静段 CER > 25% 的轮次**剔除**

有一轮安静段转写是「…窗外有几只鸟在叫，路上的人。」—— **中间断了一截**，
说明那遍没念完整（或 ASR 失败），它的 0.77× 毫无意义。
现在自动剔除并打印「有效轮数 N/M」。

### 10.1 副产物：真实往返延迟 ≈ **203–206 ms**

第 2/3 轮的对齐峰**突出度 609 / 643**（非常干净），延迟 203/206ms。
第 1 轮 189ms。与 §9.2 啁啾扫描的**最优平台 100–250ms** 完全自洽
⇒ `aec_stream_delay_ms = 150` 保持不动。

### 10.2 ⚠️ 这次比生产**更狠**（要写清楚）

噪声电平 −18 dBFS，而用户朗读约 −27 dBFS ⇒ **far 比 near 高约 9 dB**。
生产里助手的 TTS 到麦克风可与用户同级（SNR ≈ 0 dB），所以**本测试的双讲条件更严苛**。
⇒ **"8.1 倍"不能直接外推到生产的实际损伤幅度**；
能确定的只有**方向与机制**：双讲时 AEC 确实损伤近端，且不是靠回声泄漏。

### 10.3 修法方向 → **全部试过了，见 `RESEARCH-AEC-FIX-20260920.md`**（❌ 已关闭）

⚠️ 我原先在这里写的「**缩短双讲窗口**」**已作废**：那 800ms 是**误判撤销窗口**，
不是停播路径（`_begin_bargein()` 在 VAD 起音那一刻就 `pause()` 了）——
**缩短它不会让助手停得更快**。真正的双讲窗口是 **VAD 起音延迟（~500ms）**。

调研后的方向（详见该文 §8）：
1. 🟢 **拿到带 ML-REE 的 AEC3**（官方 P1 已修的正是这个症状；我们的绑定没有）
2. 🟢 同一工程顺带拿到 `EchoCanceller3Config` 的抑制器透明度调参
3. 🟡 并行：把 VAD 起音做快
4. ❌ 已实测否掉：wet/dry 混合、ASR 吃原始音频、换 Speex、target speaker extraction

### 10.4 ⚠️ 工具自身的三个坑（重踩代价高）

- **重复啁啾 → 梳状峰** → 必须用带限噪声（见上）
- `np.correlate(mode="full")` 在 20 秒（32 万样本）上是 O(N²) **会挂死** → 必须走 **FFT**
- **轮次之间只能 `flush()`，绝不能 `stop()`** —— `stop()` 关掉播放流，下一轮的
  「叮」和噪声都写进死掉的 Player（真人实测："第二次没听到叮"）。
  已加 `assert_playing()` 闸门 + 回归测试（`stop_calls == 1`）
- 开录前要**排空麦克风队列**，否则倒计时的陈旧块把第一段电平压到 −47 dBFS
