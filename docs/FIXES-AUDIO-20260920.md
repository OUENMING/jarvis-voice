### 1.1 细节

**#1 奇数块长**：Fish REST 返回的块 76/81 是奇数（如 1363、1369 字节），而链路是 int16（每样本 2 字节）。
**WS 的块是 40960（偶数）所以一直没暴露。** 修法**不能简单丢余字节**（会让后续所有样本错位半个 → 噪音），
必须**跨块携带**。另在 `Player.write` 加了显式检查，不再让 numpy 报错消失在日志里。

**#2 延迟补偿两次**（**最有价值的一条**）：
`AecGate` 把 far 参考**往前读 150ms**（物理对齐，这段对），**同时又**给
`AudioProcessor(stream_delay_ms=150)` —— 对齐后残余延迟本是 ≈0，AEC3 却按 150ms 反推 → 彻底错位。

离线实测（纯合成，真实回声延迟 150ms）：

| far 偏移 | stream_delay | ERLE |
|---|---|---|
| −150 | **150** | **1.04 dB** ❌ 曾经的配置 |
| −150 | **0** | **39.09 dB** ✅ 现在 |
| 0 | 任意 | 39 dB（**生产不可达**：镜像是回调写的，读 `emit_frames()` 恒空）|

⚠️ `stream_delay_ms` **单独**几乎无影响（0/150/300 → 39.03/39.06/39.08），**只在和 far 偏移组合时才致命**。

**#3 噪声底锁死**：`_floor == 0.0` 同时表示"未初始化"和"实测为 0"，**第一块**（很可能整块就是
启动时主人正在说的语音）直接把 floor 设成语音电平 → `need = 3×语音` → **连续说话时全被丢**。
`reset()` 也不复位 `_floor`（有 4 个调用点）。修法：前 12 块取最小 + 封顶在 `vad_min_rms`；`reset()` 一并清。

**#4 首字被 ASR 判错**（**机制与我最初的假设不同，以实测为准**）：
计划和我初判都说是「话首被切」。**能量剖面推翻了它** —— VAD 段首 100ms RMS = 8092（就是语音），
**段没被切头**。真正缺的是 **ASR 的前导上下文**。加 900ms 预滚后剖面变成
`[0, 104, …, 13, 10, 778, 8092]`，转写从「**派放**时间…」恢复成「**开饭**时间…」。详见 §3。

**#5 观测**：`player.py` 此前 **`grep latency` 命中 0** —— 从没读过 `stream.latency`，
所以 AEC 的 150ms 一直靠推断。新增 `Player.output_latency_ms`，**实测 B = 42.1ms**。
另把 `MicStream.status`（xrun）从被忽略改为记账。

## 2. ⚠️ 最重要的方法论教训：**别让探针和被测应用抢同一个音频设备**

**现象**：我跑了十几次音频探针之后，用户正常使用 jarvis 时**声音变成了男声**，
而且**断断续续、只有一两个音节**。

**根因**：我的探针在同一个进程里同时开了 `Player`（44100 输出流）和 `sd.Stream`
（16000 **双向**，含输出）→ **同一设备两个输出流** →

1. macOS 把设备标称频率切到 16000，jarvis 的 44100 数据被慢放 **44100/16000 = 2.76×**
   → 265Hz ÷ 2.76 = **96Hz = 男声**
2. 两条流抢时钟 → 丢帧 → **断断续续**

**探针关掉 → 设备回落 48000 → 恢复正常。** 这解释了「只有我测试时出问题、正常用没事」。

**⭐ 规则（写进项目）**：
- **不在 jarvis 运行时开任何音频流。** 要测，先 `./jarvis.sh stop`，确认设备空闲。
- **绝不**在同一个进程里同时开 `Player`(输出) 和 `sd.Stream`(双向) —— **用 `sd.InputStream`**
  （这正是生产形态：`MicStream`=Input + `Player`=Output）。
- 探针要能**自己退出**：加了 `run_in_background` 的探针挂死过 3 次，留下孤儿进程继续占设备。

**后果**：我此前报的所有音频实测数字（AEC 的 3.08/5.54/14.23 dB）**全部作废** —— 那些是在被
自己污染的环境里测的。

## 3. 离线验证法（本次全面转向）

被探针坑了两次之后，**改成全离线**。这些手段可靠、可重复、不碰设备：

| 手段 | 用在哪 | 为什么可靠 |
|---|---|---|
| **`ocr` 代码审查** | 发现 #2 #3 #5 | 阿里 open-code-review，走 cc-switch → **实花费 0** |
| **离线合成实验** | 定 AEC 延迟配置（39 vs 1 dB）| 纯 numpy，不碰设备 |
| **离线喂真 ASR** | 复现 + 验证 #4 | **ASR 确定性已验证**（同输入 3/3 相同）|
| **red-green 回归测试** | #3 #4 | 先在旧代码上跑**失败**，再验新代码 |
| **能量剖面** | 修正 #4 的机制解释 | 推翻了我自己的假设 |
| **`events.jsonl` 统计** | 139 条真实转写的长度分布 | 不受探针影响 |

**⭐ `ocr` 的价值在本轮得到最硬的验证：它找出的 2 个根因，我自己查了一整晚没找到。**
